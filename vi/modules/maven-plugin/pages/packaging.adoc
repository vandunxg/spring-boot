[[packaging]]
= Packaging Executable Archives

Plugin có thể tạo executable archive (jar file và war file) chứa toàn bộ dependency của application và sau đó chạy bằng `java -jar`.

Packaging executable archive được thực hiện bởi goal `repackage`:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/repackage-pom.xml[tags=repackage]
----

WARNING: Goal `repackage` không được thiết kế để dùng một mình trên command line vì nó operate trên source `jar` hoặc `war` do phase `package` tạo.
Để dùng goal này trên command line, phải include phase `package`: `mvn package spring-boot:repackage`.

TIP: Nếu dùng `spring-boot-starter-parent`, execution này đã pre-configure với execution ID `repackage` nên chỉ cần thêm plugin definition.

Ví dụ trên repackage archive `jar` hoặc `war` được build trong package phase của Maven lifecycle, gồm mọi dependency `provided` define trong project.
Nếu cần exclude một số dependency, dùng option `exclude`; xem xref:packaging.adoc#packaging.examples.exclude-dependency[dependency exclusion].

Original artifact, tức non-executable artifact, mặc định được rename thành `.original` nhưng cũng có thể giữ original artifact bằng custom classifier.

NOTE: Feature `outputFileNameMapping` của `maven-war-plugin` hiện không được support.

Module `spring-boot-devtools` và `spring-boot-docker-compose` mặc định tự động exclude; có thể control bằng property `excludeDevtools` và `excludeDockerCompose`.
Để hoạt động với `war` packaging, dependency `spring-boot-devtools` và `spring-boot-docker-compose` phải set `optional` hoặc scope `provided`.
Cũng lưu ý optional dependency mặc định không include.
Nếu define các module này optional, cũng cần set property `includeOptional` thành `true`.

Plugin rewrite manifest, đặc biệt manage entry `Main-Class` và `Start-Class`.
Nếu default không phù hợp, phải configure value trong Spring Boot plugin, không phải jar plugin.
`Main-Class` trong manifest được control bởi property `layout` của Spring Boot plugin:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/non-default-pom.xml[tags=non-default]
----

Property `layout` mặc định theo archive type (`jar` hoặc `war`). Available layout:

* `JAR`: regular executable JAR layout.
* `WAR`: executable WAR layout. Dependency `provided` đặt trong `WEB-INF/lib-provided` để tránh clash khi `war` deploy vào servlet container.
* `ZIP` (alias `DIR`): tương tự `JAR` layout dùng `PropertiesLauncher`.
* `NONE`: Bundle mọi dependency và project resource. Không bundle bootstrap loader.

[[packaging.layers]]
== Layered Jar hoặc War

Repackaged jar chứa application class và dependency trong `BOOT-INF/classes` và `BOOT-INF/lib`.
Tương tự, executable war chứa application class trong `WEB-INF/classes` và dependency trong `WEB-INF/lib` và `WEB-INF/lib-provided`.
Khi cần build Docker image từ content jar/war, hữu ích khi tách thêm các directory này để write thành distinct layer.

Layered archive dùng cùng layout với regular repackaged jar/war nhưng include additional metadata file mô tả từng layer.

Mặc định định nghĩa các layer:

* `dependencies` cho dependency có version không chứa `SNAPSHOT`.
* `spring-boot-loader` cho loader class.
* `snapshot-dependencies` cho dependency có version chứa `SNAPSHOT`.
* `application` cho local module dependency, application class và resource.

Module dependency được identify bằng cách xem mọi module thuộc current build.
Nếu module dependency chỉ resolve được vì đã install vào Maven local cache và không thuộc current build, nó được identify như regular dependency.

Order layer quan trọng vì quyết định khả năng previous layer được cache khi một phần application change.
Default order là `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application`.
Content ít khả năng change nhất nên add trước, sau đó layer dễ change hơn.

Repackaged archive mặc định include file `layers.idx`.
Để disable feature:

=== Custom Layers Configuration

Tùy application, có thể muốn tune cách layer được tạo và thêm layer mới.
Có thể làm bằng configuration load từ file hoặc classpath.

Expected matching file tại `META-INF/spring/layers/<name>.xml` trên plugin classpath.
Jar chứa configuration có thể add làm plugin dependency:

[source,xml,indent=0,subs="verbatim,attributes"]
----

----

Trong ví dụ trên, `META-INF/spring/layers/custom.xml` được expected available trên plugin classpath.

Configuration file mô tả cách archive tách thành layer và order các layer.
Ví dụ sau explicit define default ordering ở trên:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/layers.xml[tags=layers]
----

XML format `layers` define ba section:

* Block `<application>` define cách application class/resource được layer.
* Block `<dependencies>` define cách dependency được layer.
* Block `<layerOrder>` define order layer được write.

Nested block `<into>` dùng trong section `<application>` và `<dependencies>` để claim content cho layer.
Các block evaluate theo order define từ trên xuống.
Content không được block trước claim vẫn available cho block sau.

Block `<into>` claim content bằng nested element `<include>` và `<exclude>`.
Section `<application>` dùng Ant-style path matching cho include/exclude expression.
Section `<dependencies>` dùng pattern `group:artifact[:version]`.
Nó cũng có element `<includeModuleDependencies />` và `<excludeModuleDependencies />` để include/exclude local module dependency.

Nếu không define `<include>`, mọi content chưa bị block trước claim được xét.

Nếu không define `<exclude>`, không apply exclusion.

Nhìn vào example `<dependencies>` ở trên, `<into>` đầu claim mọi module dependency cho layer `application.layer`.
`<into>` tiếp theo claim mọi SNAPSHOT dependency cho layer `snapshot-dependencies`.
`<into>` cuối claim mọi thứ còn lại, trong case này dependency không phải SNAPSHOT, cho layer `dependencies`.

Block `<application>` có rule tương tự.
Đầu tiên claim content `org/springframework/boot/loader/**` cho layer `spring-boot-loader`.
Sau đó claim class/resource còn lại cho layer `application`.

NOTE: Order block `<into>` define thường khác order layer được write.
Vì vậy element `<layerOrder>` luôn phải include và _phải_ cover mọi layer reference bởi block `<into>`.

[[packaging.examples.exclude-dependency]]
=== Dependency Exclusion

Mặc định cả goal `repackage` và `run` include mọi dependency `provided` define trong project.
Spring Boot project nên xem `provided` dependency như "container" dependency cần để chạy application.
Nói chung Spring Boot project không dùng làm dependency nên ít có optional dependency.
Khi project có optional dependency, chúng cũng được include bởi goal `repackage` và `run`.

Một số dependency có thể hoàn toàn không cần và nên exclude khỏi executable jar.
Để consistent, chúng cũng không nên present khi chạy application.

Có hai cách exclude dependency khỏi packaging/runtime:

* Exclude specific artifact identify bởi `groupId` và `artifactId`, optional có `classifier`.
* Exclude mọi artifact thuộc một `groupId`.
