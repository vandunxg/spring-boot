[[packaging]]
= Đóng gói Executable Archive

Plugin có thể tạo executable archive (jar file và war file) chứa toàn bộ dependency của application, sau đó có thể chạy bằng `java -jar`.

Việc đóng gói executable archive được thực hiện bởi goal `repackage`, như trong ví dụ sau:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/repackage-pom.xml[tags=repackage]
----

WARNING: Goal `repackage` không nhằm được sử dụng độc lập trên command line vì nó operate trên source `jar` (hoặc `war`) được tạo bởi phase `package`.
Để sử dụng goal này trên command line, phải include phase `package`: `mvn package spring-boot:repackage`.

TIP: Nếu sử dụng `spring-boot-starter-parent`, execution như vậy đã được pre-configure với execution ID `repackage`, nên chỉ cần thêm plugin definition.

Ví dụ trên repackage archive `jar` hoặc `war` được build trong package phase của Maven lifecycle, bao gồm mọi dependency `provided` được define trong project.
Nếu cần exclude một số dependency, có thể dùng một trong các option `exclude`; xem xref:packaging.adoc#packaging.examples.exclude-dependency[loại trừ dependency] để biết thêm chi tiết.

Artifact gốc (tức artifact không executable) mặc định được rename thành `.original`, nhưng cũng có thể giữ artifact gốc bằng custom classifier.

NOTE: Feature `outputFileNameMapping` của `maven-war-plugin` hiện không được support.

Các module `spring-boot-devtools` và `spring-boot-docker-compose` mặc định được tự động exclude (có thể control việc này bằng các property `excludeDevtools` và `excludeDockerCompose`).
Để hoạt động với `war` packaging, các dependency `spring-boot-devtools` và `spring-boot-docker-compose` phải được set là `optional` hoặc có scope `provided`.
Cũng lưu ý rằng optional dependency mặc định không được include.
Nếu đã define các module đó là optional, cũng cần set property `includeOptional` thành `true`.

Plugin rewrite manifest và đặc biệt quản lý các entry `Main-Class` và `Start-Class`.
Nếu các giá trị mặc định không phù hợp, phải configure chúng trong Spring Boot plugin, không phải trong jar plugin.
`Main-Class` trong manifest được control bởi property `layout` của Spring Boot plugin, như trong ví dụ sau:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/non-default-pom.xml[tags=non-default]
----

Property `layout` mặc định theo archive type (`jar` hoặc `war`). Các layout sau đây khả dụng:

* `JAR`: layout JAR executable thông thường.
* `WAR`: layout WAR executable. Các dependency `provided` được đặt trong `WEB-INF/lib-provided` để tránh clash khi `war` được deploy trong servlet container.
* `ZIP` (alias của `DIR`): tương tự layout `JAR`, sử dụng `PropertiesLauncher`.
* `NONE`: Bundle toàn bộ dependency và resource của project. Không bundle bootstrap loader.

[[packaging.layers]]
== Layered JAR hoặc WAR

Repackaged jar lần lượt chứa class và dependency của application trong `BOOT-INF/classes` và `BOOT-INF/lib`.
Tương tự, executable war chứa class của application trong `WEB-INF/classes`, còn dependency trong `WEB-INF/lib` và `WEB-INF/lib-provided`.
Trong trường hợp cần build Docker image từ content của jar hoặc war, việc có thể tách tiếp các directory này để ghi chúng vào các layer riêng biệt sẽ rất hữu ích.

Layered archive dùng cùng layout với repackaged jar hoặc war thông thường, nhưng include thêm một metadata file mô tả từng layer.

Theo mặc định, các layer sau được định nghĩa:

* `dependencies` dành cho mọi dependency có version không chứa `SNAPSHOT`.
* `spring-boot-loader` dành cho các loader class.
* `snapshot-dependencies` dành cho mọi dependency có version chứa `SNAPSHOT`.
* `application` dành cho local module dependency, class của application và resource.

Module dependency được identify bằng cách xem tất cả module thuộc current build.
Nếu một module dependency chỉ resolve được vì đã được install vào Maven local cache và không thuộc current build, nó sẽ được identify là regular dependency.

Order của các layer rất quan trọng vì nó quyết định khả năng các layer trước đó được cache khi một phần của application thay đổi.
Order mặc định là `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application`.
Content ít có khả năng thay đổi nhất nên được add trước, tiếp theo là các layer có khả năng thay đổi nhiều hơn.

Repackaged archive mặc định include file `layers.idx`.
Để disable feature này, có thể làm như sau:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/disable-layers-pom.xml[tags=disable-layers]
----

=== Cấu hình Layer tùy chỉnh

Tùy application, bạn có thể muốn tune cách các layer được tạo và thêm layer mới.
Việc này có thể được thực hiện bằng configuration được load từ file hoặc từ classpath.

Để sử dụng configuration file, hãy register file đó như sau:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/custom-layers-pom.xml[tags=custom-layers]
----

Ngoài ra, configuration có thể được load từ classpath bằng cách chỉ định tên của nó.
Một file tương ứng được kỳ vọng ở `META-INF/spring/layers/<name>.xml` trên classpath của plugin.
Jar chứa configuration có thể được add làm plugin dependency, như trong ví dụ sau:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/custom-layers-classpath-pom.xml[tags=custom-layers-classpath]
----

Trong ví dụ trên, `META-INF/spring/layers/custom.xml` được kỳ vọng là available trên classpath của plugin.

Configuration file mô tả cách một archive được tách thành các layer và order của các layer đó.
Ví dụ sau explicit define order mặc định được mô tả ở trên:

[source,xml,indent=0,subs="verbatim,attributes"]
----
include::example$packaging/layers.xml[tags=layers]
----

XML format `layers` được định nghĩa trong ba section:

* Block `<application>` định nghĩa cách class và resource của application được phân bổ vào các layer.
* Block `<dependencies>` định nghĩa cách dependency được phân bổ vào các layer.
* Block `<layerOrder>` định nghĩa order mà các layer được write.

Các block `<into>` lồng nhau được dùng trong section `<application>` và `<dependencies>` để claim content cho một layer.
Các block được evaluate theo order mà chúng được define, từ trên xuống dưới.
Content không được block trước claim vẫn available để các block sau xem xét.

Block `<into>` claim content bằng các element `<include>` và `<exclude>` lồng nhau.
Section `<application>` sử dụng Ant-style path matching cho các include/exclude expression.
Section `<dependencies>` sử dụng pattern `group:artifact[:version]`.
Section này cũng cung cấp các element `<includeModuleDependencies />` và `<excludeModuleDependencies />`, có thể dùng để include hoặc exclude local module dependency.

Nếu không define `<include>`, toàn bộ content chưa được block trước claim sẽ được xem xét.

Nếu không define `<exclude>`, không có exclusion nào được apply.

Xét example `<dependencies>` ở trên, `<into>` đầu tiên sẽ claim mọi module dependency cho layer `application.layer`.
`<into>` tiếp theo sẽ claim mọi SNAPSHOT dependency cho layer `snapshot-dependencies`.
`<into>` cuối cùng sẽ claim mọi thứ còn lại (trong trường hợp này là mọi dependency không phải SNAPSHOT) cho layer `dependencies`.

Block `<application>` có các rule tương tự.
Đầu tiên, block này claim content `org/springframework/boot/loader/**` cho layer `spring-boot-loader`.
Sau đó, nó claim mọi class và resource còn lại cho layer `application`.

NOTE: Order mà các block `<into>` được define thường khác với order mà các layer được write.
Vì lý do đó, element `<layerOrder>` luôn phải được include và _phải_ cover mọi layer được reference bởi các block `<into>`.

[[packaging.examples.exclude-dependency]]
=== Loại trừ Dependency

Mặc định, cả goal `repackage` và `run` đều include mọi dependency `provided` được define trong project.
Một Spring Boot project nên xem `provided` dependency là các "container" dependency cần thiết để chạy application.
Nói chung, Spring Boot project không được dùng làm dependency, nên thường không có `optional` dependency.
Khi project có optional dependency, các dependency đó cũng được include bởi goal `repackage` và `run`.

Một số dependency có thể hoàn toàn không cần thiết và nên được exclude khỏi executable jar.
Để nhất quán, chúng cũng không nên present khi chạy application.

Có hai cách để exclude một dependency khỏi packaging hoặc runtime:

* Exclude một artifact cụ thể được identify bởi `groupId` và `artifactId`, tùy chọn thêm `classifier` nếu cần.
* Exclude mọi artifact thuộc một `groupId` nhất định.
